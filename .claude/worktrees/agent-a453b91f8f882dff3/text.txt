# SecMan

> Secure, GitHub-backed environment and secret synchronization CLI for developers working across multiple machines.

## 1. Product Overview

SecMan is a local-first CLI tool that allows developers to securely synchronize project environment variables and secrets across multiple machines using a private GitHub repository as the storage and synchronization layer.

The primary use case is:

```text
MacBook
   │
   ├── .env
   │
   └── secman push
            │
            ▼
      Private GitHub Repo
      ├── encrypted secrets
      ├── environment metadata
      └── project configuration
            │
            ▼
       secman pull
            │
            ▼
        Work PC
```

SecMan must never store plaintext secrets in the GitHub repository.

All secret values must be encrypted locally before being uploaded.

GitHub is treated as an untrusted storage/synchronization provider.

The GitHub repository must contain ciphertext, metadata, and configuration only.

# 4. Primary Design Principle

The most important security principle is:

> GitHub must never have access to plaintext SecMan secrets.

Even if somebody gains access to the private GitHub repository, they should only obtain encrypted ciphertext.

The security model should assume:

```text
GitHub = untrusted storage
SecMan = trusted encryption/decryption client
Developer = owner of encryption credentials
```

# 5. User Experience

## First machine

Developer has:

```text
my-project/
├── .env
├── package.json
└── src/
```

Run:

```bash
secman init
```

SecMan should:

1. Detect Git repository/project.
2. Ask which GitHub repository should store SecMan data.
3. Offer to create a private repository.
4. Ask for the primary environment.
5. Detect `.env`.
6. Ask whether to import it.
7. Create local encryption credentials.
8. Encrypt the secrets.
9. Create the SecMan metadata.
10. Push encrypted data to GitHub.
11. Add SecMan-specific files to `.gitignore`.
12. Never add `.env` itself to the SecMan repository.

Example:

```text
$ secman init

SecMan project initialization

Project: my-project
Environment: development

Found:
  .env

Import .env into SecMan? [Y/n]

GitHub repository:
  [Create new private repository]
  [Use existing repository]

Repository name:
  my-project-secrets

Encryption:
  Create SecMan encryption credentials

Encryption passphrase:
  ********

Confirm passphrase:
  ********

Importing 12 variables...

✓ Project initialized
✓ Secrets encrypted
✓ Private repository created
✓ Secrets synchronized

Run:

  secman run -- npm run dev
```

# 6. Second Machine

On another machine:

```bash
git clone <application-repository>
cd my-project

secman init
```

Or preferably:

```bash
secman connect
```

SecMan should identify the project and allow the developer to connect it to the existing SecMan repository.

Then:

```bash
secman pull
```

SecMan:

1. Authenticates with GitHub.
2. Downloads encrypted SecMan data.
3. Requests the encryption passphrase if required.
4. Decrypts locally.
5. Validates the data.
6. Writes `.env` only if explicitly requested.

Preferred development workflow:

```bash
secman run -- npm run dev
```

This should inject variables into the child process without requiring a plaintext `.env` file.

# 23. Encryption Architecture

This is the most security-sensitive part of the system.

SecMan must use a modern authenticated encryption algorithm.

Recommended:

```text
AES-256-GCM
```

or:

```text
XChaCha20-Poly1305
```

Use a mature, audited cryptographic library.

Do NOT implement cryptography manually.

Do NOT create custom encryption algorithms.

---

# 24. Key Derivation

For the initial personal/developer workflow, use a user-controlled passphrase.

Conceptually:

```text
User passphrase
      ↓
Password KDF
      ↓
Encryption key
      ↓
Encrypt secret bundle
```

Use a password KDF such as:

```text
Argon2id
```

with carefully selected parameters.

Never use:

```text
SHA256(password)
MD5(password)
password directly as encryption key
```

The KDF must use a unique random salt.

---

# 25. Encryption Envelope

Encrypted files should contain structured metadata.

Conceptual format:

```json
{
  "formatVersion": 1,
  "algorithm": "XChaCha20-Poly1305",
  "kdf": {
    "algorithm": "Argon2id",
    "salt": "base64..."
  },
  "nonce": "base64...",
  "ciphertext": "base64...",
  "createdAt": "...",
  "updatedAt": "..."
}
```

Do not store plaintext secrets in this structure.

---

# 26. Secret Bundle

Before encryption:

```json
{
  "DATABASE_URL": "postgres://...",
  "OPENAI_API_KEY": "...",
  "REDIS_URL": "...",
  "NODE_ENV": "development"
}
```

After encryption:

```text
plaintext
   ↓
serialize
   ↓
encrypt
   ↓
ciphertext
```

Only ciphertext goes to GitHub.

# 27. Integrity

Encryption must provide authenticated integrity.

SecMan must detect:

* [ ] Modified ciphertext
* [ ] Modified metadata
* [ ] Incorrect passphrase
* [ ] Corrupted file
* [ ] Truncated file
* [ ] Wrong environment
* [ ] Wrong project
* [ ] Unsupported encryption version

Never attempt to continue after authentication failure.

# 28. Key Handling

Never store the master encryption passphrase in:

```text

secman.yaml
Git
GitHub
plaintext config
logs
```

On supported operating systems, use the OS credential/keychain mechanism where appropriate.

For macOS:

```text

```

For Windows:

```text
Windows Credential Manager / DPAPI
```

For Linux:

```text
Secret Service / system keyring
```

If no secure keychain is available, require an explicit passphrase.

# 29. GitHub Authentication

GitHub authentication is separate from SecMan encryption.

There are two independent credentials:

```text
GitHub credential
        +
SecMan encryption credential
```

Do not combine them.

GitHub credential:

```text
Used to access repository
```

SecMan encryption key:

```text
Used to decrypt secrets
```

Compromise of one must not automatically compromise the other.

# 32. Why Separate Repository

Do not put SecMan ciphertext directly into the application's Git repository initially.

Benefits:

* [ ] Separates application source from environment state
* [ ] Prevents accidental inclusion in application history
* [ ] Allows different repository permissions
* [ ] Allows environment repository to be private
* [ ] Makes SecMan storage portable
* [ ] Allows multiple application branches to share environment state
* [ ] Reduces accidental exposure

# 41. Conflict Handling

Scenario:

Machine A:

```text
DATABASE_URL = A
```

Machine B:

```text
DATABASE_URL = B
```

Both push.

SecMan must detect remote changes.

Never silently overwrite.

Example:

```text
Conflict detected.

DATABASE_URL
  Local version: modified
  Remote version: modified

Choose:

1. Keep local
2. Keep remote
3. Resolve manually
4. Abort
```

Secret values should not be displayed during normal conflict resolution.

# 60. Security Threat Model

Assume attackers may obtain:

### Threat 1

Private GitHub repository contents.

Result:

```text
Attacker gets encrypted ciphertext.
```

They must not obtain plaintext secrets.

### Threat 2

GitHub authentication token.

Result:

Attacker may access repository, but should still not be able to decrypt secrets without the encryption key.

### Threat 3

Encrypted repository + stolen laptop data.

Security depends on the local key protection.

### Threat 4

Incorrect passphrase.

Decryption must fail safely.

### Threat 5

Tampered encrypted file.

Authenticated encryption must detect tampering.

### Threat 6

Malicious repository content.

SecMan must validate metadata and never execute repository content.

### Threat 7

Secret accidentally printed by application.

SecMan cannot guarantee protection against an application deliberately printing its own environment.

Document this limitation.

# 113. Architectural Summary

```text
                         SECMan
                           │
                           ▼
                    ┌─────────────┐
                    │     CLI     │
                    └──────┬──────┘
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ▼             ▼             ▼
          Crypto        GitHub         Local
          Module        Module         Config
             │             │             │
             │             ▼             │
             │       Private Repo       │
             │             │             │
             │       encrypted data     │
             │             │             │
             └─────────────┼─────────────┘
                           │
                           ▼
                    Local Decryption
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼                   ▼
            .env export        Runtime injection
                                    │
                                    ▼
                              Application
```

The fundamental security boundary is:

```text
             OUTSIDE TRUST BOUNDARY

                 GitHub
                    │
                    │ ciphertext
                    ▼

             ───────────────
              ENCRYPTION
             BOUNDARY
             ───────────────

                    ▲
                    │ plaintext
                    │
              Local SecMan
                    │
                    ▼
              Developer App
```

GitHub stores the data.

SecMan owns the encryption/decryption.

The developer owns the encryption credential.

The application receives secrets only when necessary.

# 114. Guiding Principle

SecMan is not initially a hosted secrets-management SaaS.

It is:

> **A local-first CLI for securely making development environments portable across machines, using GitHub as encrypted storage and synchronization infrastructure.**

The core value proposition is:

```text
Clone project
        ↓
secman connect
        ↓
secman pull
        ↓
secman run
        ↓
Development environment ready
```

The implementation should optimize for this experience while maintaining a strict security boundary around secret values.
